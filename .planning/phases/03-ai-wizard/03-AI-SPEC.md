## 1. System Classification

**System Type:** Extraction (single-shot structured content generation)

**Description:**
The AI Wizard is a server-side OpenAI pipeline that turns owner-supplied source material (pasted text or an uploaded PDF/DOCX file) plus a clarifying prompt and generation parameters (question count, difficulty) into a complete, schema-conformant quiz. It runs entirely inside a Supabase Edge Function — the OpenAI key never reaches the client. It is invoked by an authenticated quiz owner from the AI Wizard route. "Good" means the generated quiz faithfully covers the source material at the requested difficulty, returns the exact requested number of questions, marks correct answers accurately, conforms to the SPEC.md quiz JSON schema on the first or single-retry attempt, and persists cleanly into the standard `quizzes`/`questions`/`answer_options` tables so the owner lands in a ready-to-edit quiz.

**Critical Failure Modes:**
1. **Malformed / non-conformant output** — the model returns JSON that violates the SPEC.md quiz schema (missing fields, wrong types, no correct answer flagged), breaking the DB insert and stranding the owner on step 4.
2. **Wrong answer keys** — a question is generated with the `is_correct` flag on a factually wrong option, producing a quiz that scores takers incorrectly.
3. **Hallucinated content** — questions test facts not present in (or contradicting) the supplied source material.
4. **Parameter non-adherence** — the model ignores the requested question count or difficulty level, delivering a quiz that does not match what the owner asked for.
5. **Silent failure on step 4** — an OpenAI error, timeout, or invalid JSON leaves the owner on a blank or frozen screen with no error message and no recovery path.

## 1b. Domain Context

> Researched by `gsd-domain-researcher`. Grounds the evaluation strategy in domain expert knowledge.

**Industry Vertical:** Education — automated educational assessment / quiz authoring. The relevant practitioner discipline is **instructional design and psychometrics (item-writing)**: there is a well-established body of multiple-choice item-writing guidelines (Haladyna & Downing — 45 rules, condensed in later work to ~22) that test designers use to judge whether a multiple-choice question is well-formed.

**User Population:** Authenticated quiz **owners** — teachers, trainers, course authors, HR/onboarding staff, and informal content creators — who paste a text source or upload a PDF/DOCX (documentation, a book chapter, study notes) and want a ready-to-edit quiz in seconds. They are domain-knowledgeable in *their* subject matter but are **not** trained psychometricians; many will not spot a subtly flawed item. Quiz-takers (the downstream audience) never see the wizard — they take the finished quiz via a `/q/:token` link.

**Stakes Level:** **Low.** This is a low-stakes consumer SaaS tool — onboarding checks, training quizzes, study self-tests — **not** certification or high-stakes examination. Two real mitigants keep stakes low: (1) the AI output is a **draft**, not a final artifact — the owner is dropped into the standard editor and can fix or delete any question before publishing; (2) there is a human-in-the-loop review step by construction (D-02/D-03 — the wizard always lands the owner in `/editor/:quizId`). Stakes would rise to Medium only if a future phase added "publish straight from the wizard" with no edit step — it does not.

**Output Consequence:** A generated quiz becomes the **starting draft** in the owner's editor. If the owner edits carefully, flaws are caught and corrected — no taker is ever affected. If the owner trusts the draft and publishes with minimal review (the realistic common case for a "generate in seconds" tool), then any flaw ships: a question with the wrong answer key **scores takers incorrectly**, a hallucinated question tests material the source never covered, and poor distractors make the quiz trivially guessable. The downstream consequence is a mis-scored or low-quality training/study quiz — reputationally bad for the owner and frustrating for takers, but not safety-, legally-, or financially-consequential.

### What Domain Experts Evaluate Against

> Rubric ingredients in instructional-designer / item-writer language. The eval-planner (Section 5) turns these into measurable dimensions. "Domain expert" here = an instructional designer or an experienced teacher/trainer applying item-writing guidelines.

```
Dimension: Answer-key correctness
Good: The option flagged is_correct=true is genuinely the correct answer to the stem,
      and it is the ONLY correct one for a `single` question (at least one, all genuinely
      correct, for `multiple`). An expert reading the stem agrees the keyed option is right.
Bad: The keyed option is factually wrong, or a non-keyed distractor is also defensibly
     correct, or a `single` question has two arguably-correct options. The quiz would
     score a knowledgeable taker as wrong.
Stakes: Critical
Source: Foundational assessment validity — a wrong key is the one defect that directly
        produces incorrect taker scores. Maps to Section 1 critical failure mode #2.
```

```
Dimension: Source faithfulness / content validity
Good: Every question tests a fact, concept, or relationship EXPLICITLY present in the
      owner-supplied source material. The quiz measures the source, not the model's
      general world knowledge.
Bad: A question tests material absent from the source, contradicts the source, or relies
     on outside knowledge the source never establishes. The owner asked for a quiz "on
     this document" and got questions they cannot trace back to it.
Stakes: Critical
Source: Content validity — the core requirement that an assessment tests the intended
        body of material. Reinforced by the SYSTEM_PROMPT faithfulness contract (4b).
        Maps to Section 1 critical failure mode #3.
```

```
Dimension: Distractor plausibility
Good: Incorrect options are plausible to a taker who has not mastered the material —
      they reflect believable misconceptions or near-miss facts from the source — yet are
      unambiguously wrong to someone who knows it. Options are homogeneous in length,
      grammar, and specificity.
Bad: Distractors are obvious throwaways (absurd, off-topic, joke options), or one option
     is conspicuously longer / more detailed than the rest, or grammatical agreement with
     the stem gives the answer away. A test-wise taker can score well without knowing the
     material.
Stakes: High
Source: Haladyna & Downing item-writing guidelines (distractors must be plausible — able
        to attract low-performing takers); 2025 distractor-generation research (student-
        choice prediction, item discrimination index).
```

```
Dimension: Item-writing form quality
Good: Stems are clear, self-contained, and positively phrased. No "all of the above" /
      "none of the above". No negative stems unless the negative is emphasized. One
      single idea per question. Options are parallel in structure.
Bad: Negatively-phrased or double-barrelled stems, "all/none of the above" options,
     a grammatical cue (a/an, singular/plural, gender/case) that leaks the answer, or
     vague stems that only make sense once the options are read.
Stakes: Medium
Source: Haladyna & Downing 22-rule item-writing guideline set (stem-writing and
        choice-writing categories).
```

```
Dimension: Difficulty calibration
Good: The generated items match the requested D-08 level — лёгкий = direct recall of
      stated facts; средний = comprehension and connections between facts; сложный =
      application / analysis with close, near-miss distractors. The optional free-text
      difficulty prompt is honoured.
Bad: A "сложный" request yields trivial verbatim-recall questions, or a "лёгкий" request
     yields questions requiring inference the source never spells out. The cognitive
     level does not move with the slider.
Stakes: Medium
Source: Bloom's-taxonomy-based cognitive-level mapping standard in instructional design;
        2025 research notes AI-predicted difficulty correlates poorly with expert ratings
        — so this dimension must be checked explicitly, not assumed.
```

```
Dimension: Source coverage & non-redundancy
Good: For a multi-section source, questions are spread across the material rather than
      clustering on the opening paragraphs; no two questions test the same fact in near-
      identical wording. Exactly the requested question count is returned.
Bad: All questions drawn from the first part of a long source (a truncation or attention
     artefact), or several near-duplicate questions padding the count, or the count
     silently differs from what the owner requested.
Stakes: Medium
Source: Test-blueprint / content-coverage practice in assessment design. Maps to Section
        1 failure mode #4 (parameter non-adherence) and the 12k-char input truncation in
        4b Context Window Management.
```

### Known Failure Modes in This Domain

1. **Wrong answer key on a plausible-looking item.** The most damaging domain failure: the question text and options are well-formed and the flagged option is *believable*, but it is factually wrong (or a distractor is equally correct). It passes JSON-schema and Zod shape validation, passes the `single`/`multiple` correct-count refinement, and looks fine on a quick skim — so a hurried owner publishes it and takers are mis-scored. This is invisible to all code-based checks and is the primary reason an LLM-judge / human-review dimension is needed in Section 5.

2. **Plausible-but-unsourced questions (domain-specific hallucination).** The model "completes" the topic from its training data — generating a correct, reasonable-sounding question about the subject that the *supplied source* never actually covers. The owner expected a quiz on their document and gets questions they cannot locate in it. Worsened by source truncation at 12k characters (4b) when the model fills the gap from prior knowledge.

3. **Throwaway / non-homogeneous distractors.** The model produces a correct answer plus filler options that are obviously wrong (off-topic, absurd, or far shorter/longer than the key). The quiz is technically valid but trivially guessable — a test-wise taker scores high without knowing the material, defeating the quiz's purpose. A well-documented weakness of naive LLM distractor generation in the 2025 question-generation literature.

4. **Difficulty slider that does not move the cognitive level.** Regardless of лёгкий/средний/сложный, the model defaults to one register — usually mid-level verbatim recall. The owner's difficulty choice has no observable effect. Research consistently finds AI difficulty self-prediction correlates poorly with expert judgement, so this must be tested explicitly rather than assumed to work.

5. **Russian-language generation quality.** The UI and almost all source material are Russian. Failure shows up as: awkward or calque phrasing in stems/options, grammatical gender or case agreement errors between stem and options (which can also *leak the answer* — see the item-writing-form dimension), or the model drifting into English for technical terms. A flaw class an English-only eval would miss entirely — the reference dataset (Section 5) must be predominantly Russian-source.

### Regulatory / Compliance Context

No sector-specific regulatory regime applies — this is a low-stakes consumer education tool, not healthcare, legal, finance, or accredited/certification testing. There is **no** HIPAA/FCA-type constraint and no high-stakes-exam fairness/accreditation standard in scope.

One genuine, non-regulatory data-handling note: **owner-uploaded documents (PDF/DOCX) and pasted text are transmitted to a third-party processor (OpenAI)**. This is disclosed-processing rather than a compliance blocker, but two things should be true and are worth carrying into the eval/monitoring sections: (a) the owner should be informed (e.g. wizard copy or terms) that uploaded source material is sent to OpenAI for processing; (b) source text and uploaded files should not be persisted beyond what the job needs — note that per D-03 the wizard creates no `quizzes` row until success, and the `ai_jobs` table (Section 4) stores job status, not raw source content. No further regulatory action is required for this deployment context.

## 2. Framework Decision

**Selected Framework:** Official OpenAI SDK (`openai`, imported in Deno via `npm:openai`) with Structured Outputs (strict JSON-schema mode) — no agent/orchestration framework. Paired with the project's existing Zod dependency for post-generation re-validation against the SPEC.md quiz schema.

**Version:** `npm:openai@^4` (pin the exact patch at install time; v4 line is Deno-compatible via `npm:` specifier). Zod `^3.24` (already a project dependency).

**Rationale:**
Phase 3 is a single-shot structured generation call — given source text plus parameters, return one JSON quiz. There are no tools, no multi-step agent loop, no branching, no multi-agent handoff, and no retrieval corpus. An agent/orchestration framework (LangChain, LangGraph, OpenAI Agents SDK) would add abstraction overhead with zero benefit and is explicitly flagged as an anti-pattern for a well-defined single call. The official OpenAI SDK runs natively in the Supabase Edge Function Deno runtime using the same `npm:` import style Phase 2 already uses for `@supabase/supabase-js`, provides native `response_format` strict JSON-schema mode plus typed `.parse()` helpers, and adds no new infrastructure. Re-validating the parsed output with the existing Zod dependency before the DB insert gives a deterministic gate and drives the D-11 single automatic retry.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| Plain `fetch()` to OpenAI REST API | Viable (zero new dependencies) but forces hand-rolled retry, streaming, error typing, and schema-mode plumbing the SDK provides for free. Not worth it for marginal dependency savings. |
| LangChain / LangGraph | Orchestration frameworks for multi-step / stateful / branching workflows — this is a single stateless call. Matrix anti-patterns #1 and #7 explicitly warn against this. |
| OpenAI Agents SDK | Built for agent loops, tools, and handoffs — none of which this task has. Adds a runtime/mental-model layer over what is one `chat.completions` call. |
| CrewAI / Haystack / AG2 | Python-only — incompatible with the TypeScript/Deno Edge Function runtime (hard constraint). |

**Vendor Lock-In Accepted:** Yes — OpenAI is already locked by the project stack (CLAUDE.md). The SDK is a thin client over the same REST API, so swapping to plain `fetch()` (or any OpenAI-compatible endpoint) later is low-cost. No additional lock-in beyond the pre-existing provider choice.

### Entry Point Pattern

Single-shot Extraction call. The whole thing is one `chat.completions.create` with strict JSON-schema mode — no loop, no tools, no streaming.

```typescript
const openai = new OpenAI({ apiKey: Deno.env.get('OPENAI_API_KEY')! })

const completion = await openai.chat.completions.create({
  model: 'gpt-4o-mini',
  temperature: 0.4,
  max_tokens: 8000,                    // bound it — see 4b.3
  messages: [
    { role: 'system', content: SYSTEM_PROMPT },
    { role: 'user', content: buildUserPrompt({ sourceText, clarifyingPrompt, count, difficulty }) },
  ],
  response_format: {
    type: 'json_schema',
    json_schema: { name: 'quiz', strict: true, schema: QUIZ_JSON_SCHEMA },
  },
  stream: false,
})

const msg = completion.choices[0].message
if (msg.refusal) throw new Error(`OpenAI refusal: ${msg.refusal}`)   // strict mode adds this field
const quiz = QuizSchema.parse(JSON.parse(msg.content!))              // Zod re-validation gate
```

`strict: true` guarantees the JSON *parses* and matches the schema *shape*. It does **not** guarantee semantic correctness (right answer flagged, count honoured) — that is what the Zod refinement layer and the D-11 retry exist for.

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `chat.completions.create` | One stateless request/response. The entire AI surface of this phase. | The single generation call inside `waitUntil()`. |
| `response_format: json_schema` (`strict: true`) | Constrained decoding — the model can only emit tokens that keep the output valid against the supplied JSON schema. | Always, for the quiz call. Eliminates "almost-JSON" parse failures. |
| `message.refusal` | A non-null string when the model declines (safety, off-topic source). Mutually exclusive with `content`. | Check **before** `JSON.parse` — a refusal has no `content`. |
| `EdgeRuntime.waitUntil(promise)` | Keeps the worker alive to finish background work *after* the HTTP response is sent. | Wrap the OpenAI call + DB insert so the request returns < 200 ms while generation runs on. |
| `usage` (`prompt_tokens` / `completion_tokens`) | Token counts on every response. | Log to `ai_jobs` for the cost budget (4b.5) and to detect `max_tokens` truncation (`finish_reason === 'length'`). |

### Common Pitfalls

1. **`strict: true` rejects the schema unless every object has `additionalProperties: false` AND lists every property in `required`.** OpenAI strict mode does not support optional fields — there are no truly-optional keys. Model `time_limit_sec` as `["integer", "null"]` and put it in `required`; do the same for any field the model may legitimately omit. A malformed schema fails the whole call at request time, not at parse time.
2. **`max_tokens` truncation produces valid-but-incomplete output silently.** When the model hits the token cap mid-array, `finish_reason` is `'length'` and you can still get a JSON object that parses. Always check `completion.choices[0].finish_reason === 'stop'` before trusting the result; treat `'length'` as a generation failure and feed it into the D-11 retry (with a higher `max_tokens` or a lower question count).
3. **`refusal` is checked too late.** If you `JSON.parse(message.content)` without first checking `message.refusal`, you crash on `null` content for every safety refusal (e.g. the owner pastes disallowed source text). The error surfaces as a generic parse error and the real cause is lost.
4. **`waitUntil` is not awaited inside the handler — and must not be.** If you `await` the OpenAI promise before returning the `Response`, the request blocks for 10–30 s and breaks the < 200 ms SLA. If you forget `waitUntil` entirely, Deno may freeze/kill the worker the instant the response is sent and the generation never finishes. Use `EdgeRuntime.waitUntil(generate())` and return immediately. Background tasks have their own wall-clock budget (function CPU/wall limits apply) — keep the whole job comfortably inside it.
5. **`npm:openai` cold-start + the `openai/helpers/zod` subpath.** The `npm:` resolver occasionally fails to resolve deep subpaths on a cold isolate. Avoid `import { zodResponseFormat } from 'openai/helpers/zod'` in the Edge Function; hand-write the JSON schema (you need the explicit contract anyway) and use the plain `openai` root import only.
6. **The model orders `is_correct` flags but not necessarily a clean `order_index`.** `strict` mode fills every required field, but the model may emit `order_index` values that are not a tidy 0..n-1 sequence. Re-index `questions[]` and each `answers[]` array deterministically server-side after parsing — never trust the model's `order_index` for the DB insert.

## 4. Implementation Guidance

**Model Configuration:**

| Parameter | Value | Why |
|-----------|-------|-----|
| `model` | `gpt-4o-mini` | Quiz generation is structured extraction, not reasoning. `gpt-4o-mini` reaches ~100% schema adherence with strict mode at ~15x lower cost than `gpt-4o` (STACK.md). Escalate to `gpt-4o` only if eval (Section 5) shows quality is insufficient. |
| `temperature` | `0.4` | Low-but-not-zero: faithful to the source, with just enough variation to phrase distractors naturally. `0.0` tends to produce repetitive, near-duplicate distractors. |
| `max_tokens` | `~8000` for a 10-question quiz; scale to `~16000` for Pro 100-question quizzes | Bound it explicitly (4b.3). A full quiz JSON is ~250–400 output tokens per question. Under-budgeting causes the silent `finish_reason: 'length'` truncation in Pitfall 2. |
| `response_format` | `{ type: 'json_schema', json_schema: { name: 'quiz', strict: true, schema: QUIZ_JSON_SCHEMA } }` | Constrained decoding — guarantees the output shape matches `SPEC.md`. |
| `stream` | `false` | A quiz JSON is a single complete document; partial JSON is not incrementally parseable. The owner-facing progress signal is the `ai_jobs.stage` column (D-10), not token streaming. |
| `seed` | optional, fixed value | Set a `seed` if you want reproducible generations for eval-dataset regression runs (Section 5). |

**OpenAI strict JSON schema** (hand-written, lives in `_shared/quiz-schema.ts`) — mirrors the `SPEC.md` quiz JSON exactly. Every object has `additionalProperties: false` and a complete `required` list (Pitfall 1):

```typescript
export const QUIZ_JSON_SCHEMA = {
  type: 'object',
  additionalProperties: false,
  required: ['title', 'description', 'time_limit_sec', 'questions'],
  properties: {
    title: { type: 'string' },
    description: { type: 'string' },
    time_limit_sec: { type: ['integer', 'null'] },   // nullable, but still listed in `required`
    questions: {
      type: 'array',
      items: {
        type: 'object',
        additionalProperties: false,
        required: ['body', 'type', 'order_index', 'is_required', 'answers'],
        properties: {
          body: { type: 'string' },
          type: { type: 'string', enum: ['single', 'multiple'] },
          order_index: { type: 'integer' },
          is_required: { type: 'boolean' },
          answers: {
            type: 'array',
            items: {
              type: 'object',
              additionalProperties: false,
              required: ['body', 'is_correct'],
              properties: {
                body: { type: 'string' },
                is_correct: { type: 'boolean' },
              },
            },
          },
        },
      },
    },
  },
} as const
```

**Core Pattern:** "fast ACK + background generation + poll".

```typescript
// supabase/functions/ai-generate-quiz/index.ts
Deno.serve(async (req) => {
  if (req.method === 'OPTIONS') return new Response('ok', { headers: corsHeaders })
  try {
    // 1. Authenticated OWNER — verify the Supabase Auth JWT (NOT the guest jwt.ts helper).
    const supabase = createClient(
      Deno.env.get('SUPABASE_URL')!,
      Deno.env.get('SUPABASE_SERVICE_ROLE_KEY')!,
    )
    const authHeader = req.headers.get('Authorization') ?? ''
    const { data: { user } } = await supabase.auth.getUser(authHeader.replace('Bearer ', ''))
    if (!user) return json({ error: 'Unauthorized' }, 401)

    // 2. Read input. If a file was uploaded, extract text server-side (project constraint #4).
    const { title, sourceText, fileBase64, fileName, clarifyingPrompt, count, difficulty } =
      await req.json()
    const source = fileBase64
      ? await extractDocumentText(fileBase64, fileName)   // _shared/extract-text.ts
      : sourceText
    // Server-side guards: plan-aware file-size + question-count limits (D-06/D-07).

    // 3. Insert the ai_jobs row in 'pending' — this is what the client polls.
    const { data: job } = await supabase
      .from('ai_jobs')
      .insert({ owner_id: user.id, status: 'pending', stage: 'reading' })
      .select('id').single()

    // 4. Hand the slow work to a background task and RETURN IMMEDIATELY (< 200 ms).
    EdgeRuntime.waitUntil(runGeneration(supabase, job!.id, {
      title, source, clarifyingPrompt, count, difficulty,
    }))

    // 5. 202 Accepted — client now polls ai-job-status with job.id.
    return json({ jobId: job!.id }, 202)
  } catch (err) {
    console.error('ai-generate-quiz error:', serializeError(err))
    return json({ error: GENERIC_500_MESSAGE }, 500)
  }
})
```

```typescript
// runGeneration — the background task. Drives ai_jobs.stage for the D-10 progress UI.
async function runGeneration(supabase, jobId: string, input) {
  const setStage = (stage: string) =>
    supabase.from('ai_jobs').update({ stage }).eq('id', jobId)
  try {
    await setStage('generating')                       // "Составляю вопросы…"
    const quiz = await generateQuiz(input)             // OpenAI call + D-11 single retry (4b.1)

    await setStage('saving')                           // "Сохраняю…"
    const quizId = await persistQuiz(supabase, input.ownerId, quiz)   // insert quizzes/questions/answer_options

    await supabase.from('ai_jobs')
      .update({ status: 'completed', stage: 'done', quiz_id: quizId })
      .eq('id', jobId)
  } catch (err) {
    // D-11: both attempts failed. Record the error so the client shows "Повторить".
    await supabase.from('ai_jobs')
      .update({ status: 'failed', error: 'AI_GENERATION_FAILED' })
      .eq('id', jobId)
    console.error(`ai_job ${jobId} failed:`, serializeError(err))
  }
}
```

**Tool Use:** None — there are no OpenAI function/tool calls in this phase. The only "tool-like" integration is **server-side document text extraction** before the model call:

- **PDF** — `unpdf` (`extractText(await getDocumentProxy(bytes))`). It bundles a serverless build of pdf.js with no DOM dependency, which is what makes it Deno/Edge-Function safe (the stock `pdfjs-dist` and `pdf-parse` assume Node/browser globals and fail in Deno).
- **DOCX** — a `.docx` is a ZIP archive. Unzip with `unzipit`, read `word/document.xml`, strip XML tags to recover the paragraph text. Avoid `mammoth` (Node Buffer / stream dependencies that do not run cleanly on Deno).
- Both run **inside the Edge Function** (D-06, constraint #4). Enforce the plan-aware byte-size limit (Free 1 MB / Pro 5 MB) *before* extraction. After extraction, cap the recovered text at ~12,000 characters (~3,000 tokens, STACK.md) and flag truncation back to the wizard UI.

**State Management:**
- The only persistent state is the **`ai_jobs` row** — `status` (`pending|completed|failed`), `stage` (`reading|generating|saving|done`), `error`, nullable `quiz_id`, `owner_id`. The background task advances `stage`; the client polls `ai-job-status` (interval ~1.5–2 s) and reads it.
- Wizard steps 1–3 live **only in client memory** (Pinia `ai-wizard` store) — no DB row until generation succeeds (D-03). An abandoned wizard leaves nothing behind.
- The generated quiz is persisted into the **standard `quizzes` / `questions` / `answer_options` tables** via `service_role` — re-indexing `order_index` deterministically (Pitfall 6) — so the owner is redirected straight into the normal editor (`/editor/:quizId`).
- RLS on `ai_jobs`: owner reads only their own rows (`auth.uid() = owner_id`); writes are `service_role`-only from the Edge Function.

**Context Window Strategy:** `gpt-4o-mini` has a 128k context window — this single-shot call never approaches it. The real budget constraint is **input cost and `max_tokens` for the output**, not the context limit. Strategy: cap extracted source text at ~12,000 characters before the call; if the source is longer, truncate and surface a warning in the wizard (do not silently drop content). No chunking, no map-reduce, no summarisation pass — one call covers the whole source. See 4b.4.

## 4b. AI Systems Best Practices

> Written by `gsd-ai-researcher`. Cross-cutting patterns every developer building AI systems needs — independent of framework choice.

### Structured Outputs with JSON Schema + Zod

> Pydantic is Python-only. This is a TypeScript/Deno project, so the equivalent is **OpenAI Structured Outputs (`strict` JSON schema) for generation-time constraint** plus **Zod for post-parse re-validation**. The two layers are deliberately separate: the JSON schema constrains *decoding* (the model physically cannot emit malformed shape); Zod re-validates *after parse* and adds the **semantic** rules a JSON schema cannot express.

The Zod schema lives next to the OpenAI schema in `_shared/quiz-schema.ts` and adds the cross-field invariants from the SPEC.md quiz contract:

```typescript
import { z } from 'npm:zod@3.24.1'

const AnswerSchema = z.object({
  body: z.string().min(1),
  is_correct: z.boolean(),
})

const QuestionSchema = z.object({
  body: z.string().min(1),
  type: z.enum(['single', 'multiple']),
  order_index: z.number().int(),
  is_required: z.boolean(),
  answers: z.array(AnswerSchema).min(2).max(8),
})
  // Semantic rule a JSON schema CANNOT express: a `single` question has exactly
  // one correct answer; a `multiple` question has at least one.
  .refine(
    (q) => {
      const correct = q.answers.filter((a) => a.is_correct).length
      return q.type === 'single' ? correct === 1 : correct >= 1
    },
    { message: 'Question has an invalid number of correct answers for its type' },
  )

export const QuizSchema = z.object({
  title: z.string().min(1).max(120),
  description: z.string(),
  time_limit_sec: z.number().int().positive().nullable(),
  questions: z.array(QuestionSchema).min(1),
})

export type GeneratedQuiz = z.infer<typeof QuizSchema>
```

**How the framework uses it** — the OpenAI SDK enforces `QUIZ_JSON_SCHEMA` at decode time via `response_format: { type: 'json_schema', strict: true }`; the parsed object is then run through `QuizSchema.parse()`. The OpenAI strict schema catches shape errors; Zod catches semantic errors (wrong correct-answer count, empty strings, count mismatch). The requested `count` is checked separately against `quiz.questions.length` because OpenAI strict mode cannot constrain array length.

**Retry logic (D-11) — exactly one automatic retry.** The `_shared/openai.ts` `generateQuiz()` wrapper:

```typescript
export async function generateQuiz(input): Promise<GeneratedQuiz> {
  for (let attempt = 1; attempt <= 2; attempt++) {       // D-11: max 2 attempts total
    try {
      const completion = await openai.chat.completions.create({ /* …Section 4 config… */ })
      const msg = completion.choices[0]
      if (msg.message.refusal) throw new Error(`refusal: ${msg.message.refusal}`)
      if (msg.finish_reason !== 'stop') throw new Error(`finish_reason: ${msg.finish_reason}`)

      const quiz = QuizSchema.parse(JSON.parse(msg.message.content!))
      if (quiz.questions.length !== input.count) {
        throw new Error(`count mismatch: got ${quiz.questions.length}, want ${input.count}`)
      }
      return quiz                                        // success
    } catch (err) {
      console.error(`generateQuiz attempt ${attempt} failed:`, serializeError(err))
      if (attempt === 2) throw err                       // both attempts failed → caller marks ai_jobs failed
      // else loop once more — a fresh sampling usually fixes a one-off bad generation
    }
  }
  throw new Error('unreachable')
}
```

- **How many retries:** one (two attempts total), per D-11. More than one wastes the owner's time and money on a model that is consistently failing — better to surface the manual "Повторить" button.
- **What to log:** every attempt's failure reason (`refusal` / `finish_reason` / Zod issue / count mismatch) via `serializeError` to `console.error`, plus token `usage`. This is the Section 7 monitoring signal — a rising attempt-2 rate means the prompt or schema has drifted.
- **When to surface:** only after attempt 2 fails. The background task then writes `ai_jobs.status = 'failed'` with a generic `error` code; the wizard shows the Russian error + "Повторить" (steps 1–3 input preserved, no quiz row created).
- **Optional improvement:** on the retry, append the parse/validation error to the user message ("Your previous output failed validation: …; return corrected JSON") so attempt 2 is informed rather than a blind re-roll.

### Async-First Design

The Deno runtime is async-native — `Deno.serve` hands you an `async` handler and there is **no event loop to block** the way `asyncio.run()` would in Python. The framework-specific concern here is **not** awaiting vs. not-awaiting in general, but *what you await before returning the `Response`*:

- **The one common mistake:** `await`-ing the OpenAI call inside the request handler. The OpenAI call takes 10–30 s; awaiting it blocks the HTTP response and blows the < 200 ms SLA from the ROADMAP. The fix is `EdgeRuntime.waitUntil(runGeneration(...))` — Deno keeps the worker alive to finish the promise *after* the `202` response is already sent. Do **not** `await` the `waitUntil` promise; do **not** omit it (the worker may be frozen the moment the response flushes and the generation silently dies).
- **Inside the background task, do await everything** — `runGeneration` is a normal `async` function: await the OpenAI call, await each `ai_jobs` stage update, await the DB persist. Order matters (stage → generate → stage → persist → complete), so sequential `await` is correct here; there is nothing to parallelise.
- **Stream vs. await:** **await**, never stream. Streaming exists for token-by-token UX on conversational output. A quiz is one structured JSON document that is not parseable until complete, and Structured Outputs validation needs the whole payload. The owner-facing "progress" is the polled `ai_jobs.stage` column (D-10), which is honest about real processing stages — not a fake streaming animation.
- **Polling, not push:** the client polls `ai-job-status` every ~1.5–2 s. No WebSocket / SSE — polling is simpler, survives a refresh (the job id is the only state), and matches the D-12 "cannot leave step 4" constraint.

### Prompt Engineering Discipline

- **System vs. user prompt separation.** The **system prompt** is a constant (`_shared/quiz-prompt.ts`) — the role, hard rules, and the "faithfulness contract". The **user prompt** is built per-request from owner input. Never concatenate owner-supplied source text into the system prompt: keep the trusted instructions and the untrusted source in different message roles so a malicious "ignore previous instructions" inside a pasted document is far less likely to override the rules.

  ```typescript
  export const SYSTEM_PROMPT = `Ты — генератор учебных тестов. На основе ТОЛЬКО предоставленного
исходного материала составь тест.
Жёсткие правила:
- Каждый вопрос проверяет факт, ЯВНО присутствующий в исходном материале. Не выдумывай факты.
- Если материала недостаточно для запрошенного числа вопросов — всё равно верни ровно это число,
  составив вопросы по разным частям материала, без повторов.
- type "single": ровно один вариант с is_correct=true. type "multiple": два и более.
- Каждый вопрос имеет 3–5 вариантов ответа; неверные варданты — правдоподобные, но однозначно неверные.
- Соблюдай запрошенные количество вопросов и уровень сложности.
- Верни ТОЛЬКО JSON по заданной схеме, без markdown и комментариев.`

  export function buildUserPrompt(p: {
    sourceText: string; clarifyingPrompt: string; count: number; difficulty: string
  }): string {
    return [
      `Количество вопросов: ${p.count}`,
      `Сложность: ${p.difficulty}`,
      `На что сделать акцент (от автора теста): ${p.clarifyingPrompt}`,
      `--- ИСХОДНЫЙ МАТЕРИАЛ ---`,
      p.sourceText,
    ].join('\n')
  }
  ```

- **Difficulty calibration.** Map the three D-08 levels to concrete instructions in the user prompt — e.g. *лёгкий* = "вопросы на прямое узнавание фактов"; *средний* = "вопросы на понимание и связи между фактами"; *сложный* = "вопросы на применение и анализ, с близкими по смыслу дистракторами". Append the optional free-text difficulty prompt verbatim.
- **Few-shot:** inline, not retrieved. There is no corpus to retrieve from. If first-pass eval shows weak distractors, add **one** compact example quiz (1–2 questions) into the system prompt — inline is enough and keeps input tokens low. Do not build a dynamic example store for a single-shot call.
- **Token budget — never unbounded.** Always set `max_tokens` explicitly (Section 4). Leaving it unbounded in production risks a runaway generation that costs more and is more likely to truncate awkwardly. Cap the *input* by truncating extracted source text to ~12,000 characters. Both bounds are hard requirements, not nice-to-haves.

### Context Window Management

This is single-shot Extraction — there is no conversation history, no agent scratchpad, no RAG retrieval set to rerank. The 128k window of `gpt-4o-mini` dwarfs any realistic input, so the window itself is never the binding constraint. The real management job is **input sizing**:

- **Truncate at the source.** Cap extracted PDF/DOCX or pasted text at ~12,000 characters (~3,000 tokens) *before* the call. If the source is longer, truncate at a paragraph boundary and return a `truncated: true` flag so the wizard can tell the owner "материал длинный — тест составлен по первой части".
- **No summarisation pre-pass for v1.** A map-reduce summarise-then-generate pipeline would handle book-length input, but it adds a second model call, latency, and a faithfulness-loss risk (the summary drops facts the quiz then can't cover). It is explicitly deferred — `03-CONTEXT.md` scopes v1 to a single text block / single file. Revisit only if eval shows truncation materially hurts coverage on real documents.
- **Output sizing is the live concern, not input.** Scale `max_tokens` with the requested question count (Pro can ask for 100 questions). Monitor `finish_reason` — a `'length'` result means the output, not the context window, overflowed (Pitfall 2).

### Cost and Latency Budget

**Per-call cost** (`gpt-4o-mini`, approx. pricing — verify current rates on the OpenAI pricing page):

| Component | Tokens (typical 10-question quiz) | Cost |
|-----------|-----------------------------------|------|
| Input — system prompt + ~3,000-token source | ~3,400 tokens | ~$0.0005 |
| Output — 10 questions × ~350 tokens | ~3,500 tokens | ~$0.0021 |
| **Total per generation** | ~6,900 tokens | **~$0.0026** (~0.25 ₽) |

A Pro 100-question quiz scales the output ~10x → roughly **$0.02–0.03** per generation. Even at the Pro freemium ceiling (30 generations/month) the worst-case AI cost per Pro user is well under $1/month — comfortably inside the 490 ₽ price point. Free users (1 generation/month) cost a fraction of a rouble. **Conclusion: cost is not a constraint at expected volume; correctness and latency are.**

**Latency:** the `ai-generate-quiz` HTTP request returns in < 200 ms (the work is in `waitUntil`). The *background* generation takes ~8–20 s for a 10-question quiz (longer for 100). The D-10 stage-based progress UI exists precisely because this wall-clock time is real and unavoidable — set owner expectations honestly, never show a fake percentage bar.

**Caching:**
- **Exact-match cache — worthwhile.** Hash `(sourceText + clarifyingPrompt + count + difficulty)`; if an identical job already produced a quiz, the retry / re-submit can clone it instead of re-calling OpenAI. Cheap insurance against an impatient owner double-submitting step 4.
- **Semantic caching — not worth it.** Near-duplicate sources are rare for this use case and a fuzzy cache hit risks returning a subtly-wrong quiz. Skip it.
- **OpenAI prompt caching** applies automatically to the static system-prompt prefix at no extra effort — a minor input-cost saving, nothing to configure.

**Sub-task model routing:** there are no sub-tasks — it is one call, so there is nothing to route to a cheaper model. The whole pipeline already runs on `gpt-4o-mini`, the cheap tier. The only "routing" decision is the documented escalation path: if Section 5 eval shows `gpt-4o-mini` quality is insufficient on hard sources, switch the single call to `gpt-4o` — a one-line model-string change, at ~15x the (still tiny) cost.

## 5. Evaluation Strategy

> **Proportionality note.** This is a low-stakes consumer tool with a *mandatory* human-in-the-loop edit step (D-02/D-03 — the owner always lands in `/editor/:quizId` and reviews the draft before publishing). The eval strategy is deliberately right-sized: **code-based checks lead** (they are cheap, deterministic, and already half-built in the pipeline via Zod), an **LLM judge covers only the four genuinely subjective dimensions** that code cannot see, and **human review is for calibration and sampling — not every generation.** Do not expand this into a high-stakes-exam eval program; the editor step is the real safety net.

### Dimensions

Six dimensions, derived directly from the Section 1b rubric ingredients. The split is load-bearing: the first three (schema / count / correct-count) are **fully decidable by code** and the pipeline's Zod layer + D-11 retry already enforce them — they become regression assertions. The last three require an **LLM judge** because, as Section 1b's known-failure-mode #1 states, *a wrong answer key on a plausible-looking item passes every code and Zod check.*

| # | Dimension | Rubric (Pass / Fail) | Measurement | Priority |
|---|-----------|----------------------|-------------|----------|
| D1 | **Schema & shape compliance** | PASS: parsed output satisfies `QuizSchema` (Zod) — all required fields present, correct types, `time_limit_sec` integer-or-null, every question has 2–8 answers, `title` ≤ 120 chars. FAIL: any Zod parse error, or `finish_reason !== 'stop'` (silent `length` truncation). | **Code** — `QuizSchema.parse()` over each recorded dataset output; assert no throw. Reuses the exact pipeline schema from `_shared/quiz-schema.ts`. | Critical |
| D2 | **Correct-answer-count integrity** | PASS: every `single` question has exactly one `is_correct=true`; every `multiple` has ≥ 1. FAIL: a `single` with zero or ≥ 2 keyed options, or a `multiple` with none. | **Code** — the `QuizSchema` `.refine()` already in 4b; assert it holds per question. | Critical |
| D3 | **Question-count adherence** | PASS: `quiz.questions.length === requested count` for every case, including counts that strain a short source. FAIL: any mismatch. | **Code** — exact equality check (the same assertion the D-11 wrapper makes). | Critical |
| D4 | **Answer-key correctness** | PASS: for each question, the keyed option is genuinely the correct answer to the stem given the source, and for `single` it is the *only* defensibly-correct option. FAIL: keyed option is factually wrong, OR a non-keyed distractor is also defensibly correct, OR a `single` item has two arguably-right options. (Section 1b "Answer-key correctness"; failure mode #1.) | **LLM Judge** (calibrated) + **Human** spot-check on disagreements. Judge is given the source text + question + options and rules pass/fail per question. | Critical |
| D5 | **Source faithfulness** | PASS: every question tests a fact / concept / relationship explicitly present in the owner-supplied source. FAIL: a question tests material absent from, or contradicting, the source, or relies on outside world knowledge. (Section 1b "Source faithfulness"; failure mode #2 — worsened by 12k-char truncation.) | **LLM Judge** (calibrated). Judge receives the (truncated, as-sent) source + each question; rules grounded / not-grounded per question. | Critical |
| D6 | **Distractor plausibility, item-form & difficulty** | PASS: distractors are plausible near-misses, homogeneous in length/grammar/specificity; no «все перечисленное» / «ничего из перечисленного»; stems are single-idea, positively phrased, with no grammatical (род/число/падеж) cue leaking the answer; cognitive level moves with the D-08 slider (лёгкий = recall, средний = comprehension, сложный = application/analysis); questions are spread across a multi-section source with no near-duplicates. FAIL: throwaway/absurd distractors, conspicuous length outlier, agreement cue, banned option forms, difficulty flat across levels, or questions clustered on the source's opening paragraphs. | **LLM Judge** 1–5 score (a composite of Section 1b's distractor / item-form / difficulty / coverage dimensions — merged because all are quality signals feeding the flywheel; none gates a release on its own). **Human** calibration. | High |

**Calibration gate (Verify phase).** Before the D4/D5/D6 LLM judge is trusted, an instructional designer / experienced teacher-trainer labels the full reference dataset by hand; the judge must reach **≥ 0.7 agreement** with those human labels (per `ai-evals.md`). Until calibrated, judge output is advisory only — D1–D3 (code) are the actual release gate.

### Eval Tooling

**Primary Tool:** **Vitest** (code-based dimensions D1–D3) + **Promptfoo** (prompt-regression harness and LLM-judge assertions for D4–D6).

**Override of the workflow default (Arize Phoenix).** Phoenix is *not* adopted here, and the override is deliberate. Phoenix is a Python / OpenTelemetry-centric tracing platform; this phase's runtime is a TypeScript **Deno** Supabase Edge Function with no Python in the stack and a solo / small team. Standing up a Phoenix server is disproportionate for a single-shot extraction call. Instead:
- **D1–D3 are pure assertions** — they belong in **Vitest**, the harness the team already runs (`npm test`). The eval cases run the *real* `_shared/quiz-schema.ts` `QuizSchema` against recorded generations.
- **Promptfoo** is CLI-first, needs no platform account, has native `llm-rubric` / `javascript` assertion types, and is purpose-built for *structured-generation prompt regression* — exactly this use case (`ai-evals.md` recommends Promptfoo + code-based validators for structured extraction). It runs as a Node step in CI, decoupled from the Deno function.
- **Production tracing** is the **`ai_jobs` table itself** plus structured `console.error` logs in the Edge Function (Section 7) — already specified in Section 4. No extra tracing infrastructure is warranted.

### Reference Dataset

**Size:** **15 cases** to start (within the `ai-evals.md` 10–20 band). Small and high-quality beats large and mediocre — expand only from real production failure modes (Section 6 flywheel), not hypothetical coverage.

**Composition:** every case is `{ source material, clarifyingPrompt, count, difficulty }`. **Predominantly Russian-source** — Section 1b failure mode #5 (Russian-language quality, gender/case agreement leaks, English drift) is invisible to an English-only dataset.

| Cases | Type | Covers |
|-------|------|--------|
| 5 | **Critical path** | Realistic owner inputs: a book chapter, a documentation page, study notes, an onboarding policy doc, a how-to article — Russian, 1.5k–8k chars, counts 5 / 10 / 10. |

D1–D3 need no human labels — they are decided by code. **Build the dataset concurrently with implementation** (`ai-evals.md` Execute-phase guidance), not after — the first 5 critical-path cases can come from the developer's own manual wizard test runs.

## 6. Guardrails

> **Honest scoping.** The pipeline already contains a genuine, real-time correctness gate — it was specified in Section 4b, not invented here. The online guardrails below are that existing gate, named explicitly. The subjective dimensions (D4–D6) **cannot be online guardrails**: an LLM-judge call per generation would roughly double latency and cost, and — critically — it is unnecessary, because the mandatory editor step (D-02) is the human review. So D4–D6 run **offline only**, as the improvement flywheel. No guardrail is invented that the system does not need.

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| **Zod re-validation gate** (D1 + D2) | `QuizSchema.parse()` throws — shape error, empty string, or wrong `is_correct` count for the question type. Runs in `_shared/openai.ts` `generateQuiz()` before any DB insert. | **Block + retry.** Attempt-1 failure triggers the D-11 single retry (optionally with the validation error appended to the user message). Attempt-2 failure → `ai_jobs.status='failed'`, generic Russian error + "Повторить". No malformed quiz ever reaches `quizzes`. |
| **Count + completeness check** (D3) | `quiz.questions.length !== requested count`, or `finish_reason !== 'stop'` (silent `length` truncation, Pitfall 2). | **Block + retry**, same D-11 path. A truncated or short quiz is treated as a generation failure, not delivered. |
| **OpenAI refusal check** | `completion.choices[0].message.refusal` is non-null (safety refusal on disallowed pasted source). | **Block.** Surface as a generation failure with the Russian error + "Повторить"; never `JSON.parse` null content (Pitfall 3). |
| Answer-key correctness / faithfulness / item quality (D4–D6) | — | **N/A as an online guardrail — by design.** Not catastrophic (low stakes + mandatory editor review per Section 1b), and an inline LLM-judge call is not worth the latency/cost. Handled by the offline flywheel below. |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|-------------------|-----------------------|
| **Retry rate** (attempt-2 share) — proxy for D1–D3 drift | 100% — derived from `ai_jobs` + `console.error` logs, no sampling needed. | Sustained rise above the Section 7 threshold → re-run the full Promptfoo gate; inspect for prompt / schema / model drift. A rising retry rate is the earliest signal `QUIZ_JSON_SCHEMA` or `quiz-prompt.ts` has drifted. |
| **Answer-key correctness** (D4) | Run the calibrated LLM judge on a **monthly sample of ~20 completed generations**, weighted toward signal cases (see Section 7 sampling). Plus the 15-case reference dataset on every pre-release run. | Sample pass rate < 95% → human review of the failures; revise the `SYSTEM_PROMPT` faithfulness / answer rules or escalate the model to `gpt-4o` (the documented 4b escalation path). |
| **Source faithfulness** (D5) | Same monthly ~20-generation sample; full reference dataset pre-release. | < 90% grounded → tighten the faithfulness contract in `SYSTEM_PROMPT`; investigate whether 12k-char truncation is causing the model to fill gaps from prior knowledge (failure mode #2). |
| **Item quality — distractor / form / difficulty** (D6) | Same monthly sample; full reference dataset pre-release. | Mean < 3.5/5 → prompt-engineering iteration: add one inline few-shot example quiz (4b), strengthen the difficulty-level instructions. |
| **Owner edit intensity** (product signal) | Sampled — proportion of AI-generated questions edited or deleted in the editor within 24 h of generation. A high edit/delete rate is a real-world quality proxy that needs no LLM judge. | A sustained spike, especially one divergent from the D4–D6 judge scores, is **signal-metric divergence** (`ai-evals.md`) — investigate manually; it may reveal a failure mode the rubric misses. |

## 7. Production Monitoring

**Tracing Tool:** **No dedicated tracing platform** — the `ai_jobs` table is the trace store, supplemented by structured `console.error` logs in the Edge Function (viewable in the Supabase Edge Function logs / dashboard). This is the proportionate choice for a single-shot call on a Deno runtime with a small team (see the Section 5 Phoenix override). Recommended additions that make `ai_jobs` monitorable without new infrastructure: persist per-job `attempt_count`, `finish_reason`, `prompt_tokens`, `completion_tokens`, `failure_reason` (refusal / finish_reason / zod / count-mismatch), and `duration_ms` alongside the existing `status` / `stage` / `error` columns. A scheduled Supabase SQL query (or a lightweight dashboard) aggregates these.

**Key Metrics to Track:**
1. **Generation success rate** — `completed` / (`completed` + `failed`) over `ai_jobs`. The headline health metric.
2. **Retry rate** — share of successful jobs that needed attempt 2. The earliest drift signal for D1–D3 (a rising rate means prompt / schema / model drift).
3. **Hard-failure rate & breakdown** — share ending `status='failed'`, split by `failure_reason` (refusal vs. finish_reason vs. zod vs. count-mismatch) — tells you *which* failure mode is growing.
4. **Generation latency** — background wall-clock from `pending` to `done` (target ~8–20 s for a 10-question quiz; longer for a Pro 100-question quiz). Distinct from the < 200 ms HTTP-ACK SLA, which is also monitored.
5. **Token usage / cost per generation** — `prompt_tokens` + `completion_tokens` from `usage`; trends cost and flags truncation risk. (Cost is not a constraint at expected volume per 4b — tracked for anomaly detection.)

**Alert Thresholds:**
- **Page / urgent:** generation success rate < 90% over a rolling 24 h, OR hard-failure rate > 10% — the wizard's core promise is broken.
- **Investigate (non-urgent):** retry rate > 20% sustained over a week (D1–D3 drift — re-run the Promptfoo gate); OR p95 generation latency > 45 s; OR `finish_reason='length'` on > 5% of jobs (raise `max_tokens` or cap the count).
- **Cost anomaly:** mean tokens-per-generation rises > 50% week-over-week with no count change — points to prompt bloat or runaway output.

**Smart Sampling Strategy:** human review and the monthly LLM-judge run (Section 6 flywheel) do not sample uniformly — they weight toward **concerning signals**, per `ai-evals.md`:
- **Retried jobs** (attempt 2 succeeded) — the model struggled; the result is more likely to be subtly flawed.
- **Boundary inputs** — source near the 12k-char truncation cap, or a high requested count against a thin source (the count-pressure cases most prone to D5 hallucination).
- **High owner edit/delete intensity** — quizzes the owner heavily reworked in the editor within 24 h; a strong real-world quality signal and the primary input for detecting signal-metric divergence.
- **`сложный` difficulty requests** — Section 1b flags AI difficulty calibration as the weakest dimension; over-sample hard-difficulty generations.
- A small **uniform-random baseline** (~5 jobs/month) alongside the signal-weighted sample, so genuinely new failure modes that produce no upfront signal still surface.
